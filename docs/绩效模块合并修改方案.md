# 绩效管理「三模块合并」修改方案

> **合并对象**：年终考核汇总（paYearly）+ 互评管理（paPeerMgmt）+ 我的互评任务（paPeerReview）
> **合并目标**：三者归入「年度绩效管理」一个二级模块，互评管理 / 我的互评任务 / 年终考核汇总成为其下三个子页面
> **项目性质**：纯前端原型，无后端、无构建；本文档只出方案，不动代码

---

## 一、现状分析

### 1.1 菜单现状（绩效管理板块，7 个二级子系统）

| order | key | 名称 | 图标 | actions |
|---|---|---|---|---|
| 2 | paTemplate | 考核模板管理 | 📋 | view / add / edit |
| 3 | paTableMonthly | 月度绩效考核 | 📅 | view / edit |
| 4 | paTableYearly | 年度绩效考核 | 🎯 | view / edit |
| 5 | paPeerMgmt | 互评管理 | 👥 | view / edit |
| 6 | paPeerReview | 我的互评任务 | ✍️ | view |
| 7 | paResult | 结果查询 / 检索 | 🔎 | view / export |
| 8 | paYearly | 年终考核汇总 | 🏆 | view / edit |

### 1.2 三者业务上本是一条链路（数据层已天然一体）

三个视图操作的是**同一份数据**——`PA_TABLES` 中 `type:"yearly"` 的年度考核表：

- `peerReviewers`（互评人名单）——互评管理页维护（openEditPeerReviewers / savePeerReviewers）
- `peerScoreDetails[当前用户]{items, score, submittedAt}`——我的互评任务页写入（saveAllPeerReviewScores）
- `peerScores{avg, n, submitted}`——随打分自动汇总（autoCalcPeerScores）
- 年终汇总页的「互评平均分」列直接读取 `peerScores.avg`

业务链路：**配置互评人 → 被分配人打分 → 自动汇总平均分 → 年终汇总采纳**。三个菜单是同一流程的三段，合并是层级归位，不是新功能。

### 1.3 平台三级架构基础设施已齐备（关键结论）

调研确认：门户三级模型（板块 → 二级子系统 → 三级子项）的基础设施**已全部建成**，目前全平台没有任何种子菜单实际使用三级——本次合并是三级架构的第一个真实用例，且**不需要新写任何基础设施代码**：

| 能力 | 位置 | 状态 |
|---|---|---|
| 三级路由 selectSubSub + renderCurrent 的 `VIEWS[curSubSub]()` 分发 | router.js | 已实现 |
| 三级磁贴分组页 renderSubGroupHome（二级有子项时自动进入） | views.js / router.js `_renderSubLevel` | 已实现 |
| 三级面包屑 + 逐级点击回跳 | router.js renderCrumb | 已实现 |
| 路由持久化 `{m, v, ss}` 与刷新恢复 | router.js saveRoute / restoreRoute | 已实现 |
| 权限递归 hasRole（任意深度）+ 父节点语义 | auth.js `_checkPermsSubs` | 已实现 |
| 权限配置弹窗三级树 | auth.js `_collectPermsLevel` | 已实现 |
| 菜单种子递归构建 `_buildSubsFromSeed` | config-menu.js | 已实现 |
| 种子变更时旧结构自动迁移（平铺 → 嵌套） | config-menu.js `_syncSubsMissing` | 已实现 |
| 菜单管理页任意深度编辑 | views-sys.js `_renderSubRows` | 已实现 |
| 权限变更后三级页降级处理 | router.js refreshAfterPermChange | 已实现 |

父节点权限语义已核实：`hasRole('perf', '父key')` 在「任一子项获授权」时返回 true（auth.js `_checkPermsSubs` 第 80 行）——磁贴点击、fav 跳转分组页等场景无需额外处理。

## 二、方案 A（推荐）：菜单三级嵌套

### 2.1 合并后的菜单结构

绩效管理板块 7 → 5 个二级子系统：

| order | key | 名称 | 说明 |
|---|---|---|---|
| 2 | paTemplate | 考核模板管理 | 不变 |
| 3 | paTableMonthly | 月度绩效考核 | 不变 |
| 4 | paTableYearly | 年度绩效考核 | 不变 |
| 5 | **paYearlyMgmt** | **年度绩效管理** 📊 | 新二级父节点，无自有页面，点击进入三级磁贴分组页 |
| 6 | paResult | 结果查询 / 检索 | 不变（order 由 7 顺延） |

`paYearlyMgmt` 下三个三级子项（**key 全部保持现名**，这是零视图改动的关键）：

| 三级 key | 名称 | 图标 | 承载视图 |
|---|---|---|---|
| paPeerMgmt | 互评管理 | 👥 | renderPaPeerMgmt（原样复用） |
| paPeerReview | 我的互评任务 | ✍️ | renderPaPeerReview（原样复用） |
| paYearly | 年终考核汇总 | 🏆 | renderPaYearly（原样复用） |

**交互路径**：工作台 → 绩效管理（板块磁贴）→ 年度绩效管理（二级磁贴）→ 三级磁贴分组页 → 点击进入具体页面。
**面包屑**：工作台 / 绩效管理 / 年度绩效管理 / 互评管理（逐级可点）。

### 2.2 为什么视图 / 路由 / 权限种子可以零改动

- **视图分发**：renderCurrent 对三级页执行 `VIEWS[curSubSub]()`，与二级页的 `VIEWS[sub.key]` 是同一套查表逻辑；三个 VIEWS 注册 key 不变，注册代码一行不动。
- **页面头部**：三个 render 函数均使用 `pageHeader(PAGES.<key>.title, PAGES.<key>.desc)`，key 不变 → strings.js 的 PAGES / TH 全部不动。
- **角色权限种子**：ROLE_EXTRA_ACTIONS 是「模块 → 叶子 key」扁平映射，`_buildRoleSubsPerms` 递归时始终透传 moduleKey，叶子 key 不变 → 授权结果与现在完全一致（supervisor / deptLeader 的 perf 授权原样生效）。
- **路由**：selectSubSub / restoreRoute / refreshAfterPermChange 均已支持三级。

### 2.3 改动清单（共 2 个文件，约 25 行）

| 文件 | 改动 | 量级 |

| js/modules/config-menu.js | DEFAULT_MODULES.perf.subs：删除 paPeerMgmt / paPeerReview 两个平铺项；paYearly 平铺项替换为 paYearlyMgmt 父节点（内嵌三个子项）；paResult order 7 → 6 | ~20 行 |
| js/modules/strings.js | SUB_DESC 增加 paYearlyMgmt 描述（模块磁贴副文案）；PAGES.paYearlyMgmt 可选补充 | ~4 行 |
| 视图 / 路由 / 权限种子 / 数据层 | 均不动 | 0 |

### 2.4 旧数据自动迁移（用户 localStorage 里的旧菜单）

loadMenus 的种子指纹机制自动处理，**无需写迁移代码**：

1. DEFAULT_MODULES 变更 → 种子哈希变化 → `_syncSeedIfChanged` 触发一次同步；
2. `_syncSubsMissing` 把新父节点 paYearlyMgmt（含三个子节点）按 order 插入 perf.subs；
3. 平铺的旧 paPeerMgmt / paPeerReview / paYearly 不在种子 key 集合中 → 自动清理（非用户自建节点）；
4. 发生变更 → `rebuildAllPermsFromDefault()` 全角色 perms 按新结构重建（sysAdmin 全量；内置角色按 ROLE_EXTRA_ACTIONS；自定义角色重置为默认 view+export——与历史上每次种子变更的平台行为一致）；
5. 刷新前残留的旧路由（如 v=paPeerReview）恢复时 findMenuNode 找不到 → 优雅降级到绩效管理板块首页。

### 2.5 兼容性影响评估

| 影响面 | 结论 |
|---|---|
| 数据层（PA_TABLES / PA_RESULTS） | 零影响——三者本就共享同一批 yearly 表 |
| 全局搜索 | 零影响——搜索源只有标准库 / 经验案例 / 过程资产，绩效内容从未纳入索引 |
| fav 常用应用 | 旧收藏中的 paPeerMgmt / paPeerReview 被失效过滤，列表为空时回退默认前 4 个；新父节点「年度绩效管理」自动成为候选，点击直达分组页（openFavApp → _renderSubLevel → renderSubGroupHome 链路已核实通畅）。**零代码改动**；若希望 fav 直达三级页，可作后续增强（_favCandidates 递归 + openFavApp 传 subSub） |
| 菜单管理页 | 管理员可见嵌套结构，父节点带「3 项」徽章，可任意深度增删改 |
| 角色权限配置 | 权限树自动变三级，勾选 / 保存逻辑已递归支持 |
| 自定义角色 | 种子变更时 perms 重置为默认（既有平台语义），需在角色管理重新勾选——原型阶段可接受 |
| 三级页返回按钮 | 现有行为回到板块首页；面包屑父级链接可回分组页（三级页首个用例，实现时可评估是否将返回按钮改为回父级） |

## 三、方案 B（备选）：单页内 Tab

保留一个二级菜单「年度绩效管理」，在一个页面内用 Tab 切换三个功能。

做法：新增容器视图 renderPaYearlyMgmt，内部 tab 切换；三个 render 函数从「返回整页」改为「返回 tab 面板内容」；tab 状态存 localStorage；每个 tab 手动 hasRole 控制显隐。

- **优点**：无跳转、单屏切换；菜单更扁平。
- **缺点**：
  1. 三个视图的返回结构要重构（剥离 pageHeader / toolbar 或改为面板内标题），改动量明显大于 A；
  2. tab 无法复用三级路由、刷新恢复、面包屑，需手写状态持久化；
  3. 权限粒度要手写判断，绕开平台统一的 perms 树；
  4. 与全平台「磁贴导航」的门户模型不一致，成为特例。

## 四、两案对比与推荐

| 维度 | A 三级嵌套 | B 单页 Tab |
|---|---|---|
| 数据层 | 0 改动 | 0 改动 |
| 视图层 | 0 改动（三个 render 原样复用） | 3 个视图返回结构重构 |
| 路由 / 权限基础设施 | 0 改动（已建成） | 手写 tab 状态 + 权限判断 |
| 菜单种子 | ~20 行 | ~10 行 |
| 刷新恢复 / 面包屑 | 平台原生支持 | 需手写 |
| 与平台架构一致性 | 完全一致 | 特例 |
| 预计工作量 | 1 个迭代轮次（含七套回归） | 1.5 ~ 2 个轮次 |

**推荐方案 A**：把「合并」表达为菜单层级关系的归位，复用平台全部既有能力；风险集中在种子迁移一处，而该处逻辑是平台已验证过的代码路径。
