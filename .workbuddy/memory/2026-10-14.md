## 修复：公告表单「置顶展示」复选框被全局样式拉伸（用户截图反馈）

**现象**：新增/编辑公告弹窗中，「置顶展示」行的复选框被拉宽、提示文字「置顶后将在工作台……」被挤到行尾远右端，布局错乱。

**根因**：`.form-control input{width:100%}`（特异性 0-1-1）命中 `input[type="checkbox"]`，而代码库既有的 width:auto 豁免只覆盖 `.form-control .radio-group input[...]`（0-2-1）和 `.check-item input[...]` 两个场景——公告表单的复选框不在任何豁免内，作为 flex 子项被按 100% 基宽参与收缩计算，视觉上即"复选框变宽+文字被挤走"。与 header 搜索框同属第五类坑（全局元素规则静默破坏组件样式）的第三次现身。

**修法**：
- `js/modules/views-sys.js`：`openAddNotice`/`openEditNotice` 两处把手写内联 flex 的 label 换成语义类结构 `<label class="chk-inline"><input type="checkbox" id="ntcTop"><span class="chk-tip">…提示…</span></label>`（提示文字独立 span，12px 灰色，可自然换行）。
- `css/style.css`：在 `.radio-group` 复选框豁免规则旁新增 `.form-control .chk-inline` / `.form-control .chk-inline input[type="checkbox"]`（**0-2-1 压过 0-1-1**，width:auto + flex-shrink:0 + accent-color）与 `.chk-tip`；加防回归注释，明确"新增表单复选框一律套 .chk-inline，勿手写内联 flex"。

**验证（四层全绿）**：
- 层叠模拟器扩展第 7 节：对 `input#ntcTop`（label.chk-inline > .form-control 祖先链）计算胜出声明——width 来自 `.form-control .chk-inline input[type="checkbox"]` 值 `auto`、flex-shrink=0，15 项断言全过。
- 布局探针新增 7 项断言（新增/编辑弹窗均含 chk-inline/chk-tip/ntcTop、旧内联 flex 写法不复现、编辑态 checked 保留）：17 项全过。
- 冒烟/功能/门户三套回归对 r4 基线零差异（windowKeys 零增减、renders 零变化、功能断言 42 项无失败）——弹窗标记层不影响 VIEWS 渲染。
- views-sys.js 语法通过；CSS 大括号 436/436 配平。

**教训（第七条）**：本项目 `.form-control input{width:100%}` 对**复选框/单选框**同样生效——凡表单内嵌 checkbox，必须套 `.chk-inline`（或既有 `.radio-group`）类获取 width:auto 豁免，裸 input 必被拉伸。写这类组件时先用层叠模拟器核实 width 胜出者。

- `js/modules/strings.js`：新增 `MODULE_DESC`（4 个内置板块描述文案，对照设计稿；自定义模块无描述时不渲染 desc 行）。
- `css/style.css`：`.portal-grid-modules{grid-template-columns:repeat(var(--cols,6),minmax(0,1fr))}`、`.portal-grid-fav` 同理（默认 4）；`.portal-module-tile` 改 `flex-direction:column`+白底+左色条保留；响应式分档用复合选择器 `.portal-grid.portal-grid-modules`（0-2-0 压过基础规则的 0-1-0）：≤1200px 三列/≤768px 两列/≤480px 单列；fav ≤1200px 四列/≤768px 两列/≤480px 单列。

**关键技术决策——列数封顶方案**：CSS Grid 无"最多 N 列"原生表达（auto-fill+minmax 在宽屏必超封顶；固定 repeat(N) 在卡片不足 N 时留空轨道且卡片被拉窄）。采用 **JS 算列数写入 CSS 变量 + var() 进 repeat() 次数**：`repeat(var(--cols,6),minmax(0,1fr))`。内联只设 `--cols` 不设 grid-template-columns，媒体查询因此可正常覆盖（否则内联优先级最高会锁死响应式）。效果：3 板块→3 等宽卡（与设计稿一致）、5 板块→5 卡、≥6→6 卡封顶。

**验证（四层全绿）**：布局探针扩到 36 项布尔断言（--cols 公式 min(count,6)/min(count,8)、staff 4 卡→4 列、admin 5 卡→5 列证明非硬编码、新结构四类元素数量与卡片数一致、旧 meta/arrow 结构不复现、CSS var 规则与三档响应式存在）；冒烟/门户/功能三套对 round6 基线——仅 home 按设计变化（6155→6410），windowKeys 零增减；CSS 大括号 447/447。

## 第 18 轮：修复菜单管理删除后被种子恢复（持久化语义重构）

**教训（第十八条）**：「种子数据 + localStorage 持久化 + 每次加载同步」是经典陷阱组合——同步逻辑必须回答「用户的删除/修改与种子的缺失/变更如何区分」。指纹闸门（种子变更才同步）+ 墓碑（删除永久生效）+ custom/edited 标记（用户数据不被覆盖）三件套是这类问题的通用解法。另：修持久化 bug 必须做**阴性对照**（旧代码跑新探针应失败），否则「探针全过」可能只是没测到那条路径——本轮 19 项旧代码失败就是探针有效性的证明。还踩了探针自身调用错误：`updateMenu(path, key, patch)` 三参写成两参导致改名假失败，写探针先核对产品函数签名。
